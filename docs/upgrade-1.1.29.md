# NPS 1.1.29 升级说明

本文说明从 1.1.28 升级到 1.1.29 时的行为、配置变化和回滚方法。

## 本版本变化

- NPC 与 NPS 的 Bridge 握手按客户端版本自动分流：NPC `1.1.28` 及以下继续使用原握手；`1.1.29` 及以上使用带随机挑战和时间窗口的新握手。无需给现有 NPC 统一升级，也不需要切换配置开关。
- 隧道和域名规则可以配置后端健康检查，以及独立的上行、下行限速。只有理解新控制消息的 NPC（`1.1.29` 及以上）会接收 Web 配置的健康检查；旧 NPC 继续采用本地配置。
- Bridge 可选并行启用 KCP、WebSocket、WebSocket TLS 和 QUIC 监听。端口默认关闭（`0`）；QUIC 使用独立 UDP 端口和 TLS ALPN，当前不是面向浏览器的 HTTP/3 Host 反向代理，也不改变现有 TCP/TLS Bridge 端口。
- API 补充资源限速、健康检查和访问地址字段；Host 列表明确返回 HTTP/HTTPS 对外端口，TCP 隧道提供完整访问地址。字段缺省时保持旧调用方式可用。
- 客户端、用户、Host 和隧道的编辑页面支持按组展开/收起；基础信息默认可见，高级配置默认收起。收起仅改变显示，不禁用或清空字段。

## 升级前准备

1. 备份 NPS 可执行文件和整个 `conf/` 目录，至少保留 `nps.conf`、`clients.json`、`tasks.json`、`hosts.json`、`global.json`、`users.json` 及证书/私钥文件。
2. 记录当前 Bridge、HTTP/HTTPS、Web 管理端口，以及正在使用的证书文件路径。
3. 确认新服务端程序可读取原有配置目录，文件属主和读写权限正确。

生产环境需要短暂重启 NPS，因为新旧程序不能同时占用相同监听端口。NPC 会按现有重连策略重新连接；这属于短暂切换，不是零中断热替换。真正的零中断切换需要另行准备并行服务器和入口流量切换。

## 配置文件如何变化

首次启动 1.1.29 时，服务端会把新版模板中缺少的必需配置项追加到现有 `conf/nps.conf`。它不会覆盖已有值（包括显式空值）、删除注释或自定义项，并通过同目录临时文件替换来避免写入一半的配置。通过 Web 面板关闭并移除的可选监听、证书、日志和调试配置不会在下次启动时被重新添加。兼容旧配置别名时，会补写当前版本识别的字段，原别名保留；若规范字段已经存在，规范字段优先。

配置页仍会展示完整的内置配置目录，即使某个可选键当前没有写入文件。只有启用该功能时才需要勾选“启用此配置”并保存；例如并行 Bridge 端口、IP 登记独立监听、P2P/pprof、证书路径和日志归档参数都可以保持未配置。不要为了补字段而把登记密钥或 TOTP 密钥复制到文档、工单或公开消息中。

自动维护范围仅为服务端的 `conf/nps.conf`。NPS 不会改写 NPC 的 `npc.conf`，也不会删除或重新生成 `clients.json`、`tasks.json`、`hosts.json`、`global.json`、`users.json` 或现有证书。旧 JSON 缺少本版本新增字段时会按安全默认值读取；数据文件在被 Web/API 修改并保存后才会包含相应新字段。

### 旧生产配置字段的处理

升级器不会删除未知字段，也不会把旧配置重排成新模板。像 `runmode`、`appname`、
`https_just_proxy`、`https_default_cert_file` 和 `https_default_key_file` 这样的历史字段
可以继续留在文件中，但当前运行逻辑不再依赖它们：

- 管理面板和 Host 规则的 HTTPS 终止由 `web_open_ssl`、`web_cert_file`、`web_key_file`，以及 Host 自身的证书字段控制。
- HTTPS 原样透传仍通过 Host 的端口转发/客户端目标配置实现，不由 `https_just_proxy` 决定。
- `appname` 和 `runmode` 仅作为历史注释保留，不会改变当前多用户、日志和代理行为。

如果希望配置文件更干净，可以在确认所有服务已切换并完成备份后手工删除这些字段；不删除也不会影响升级回滚。程序不会自动替用户删除它们。

## 新增或可能生成的文件

- `conf/instance.key`：Web 会话签名密钥。未配置 `instance_key_file` 时由服务在首次使用会话密钥时创建；应随配置目录一起备份，删除后原有 Web 登录会话会失效。
- `audit.log`：管理员操作审计日志，在发生可审计操作后生成；不保存密码、API Token、证书私钥或代理请求/响应正文。
- 轮转日志归档：由 `log_path`、`log_max_size`、`log_max_files`、`log_max_days`、`log_compress` 和 `log_rotate_daily` 控制；会与活动日志放在同一目录。

本次升级不要求新增证书文件、Geo 数据库或新的 JSON 数据文件。现有 `server.pem`、`server.key` 和平台域名证书路径保持不变。

## NPC 与多用户兼容

| NPC 版本 | 握手 | 原有隧道 | 新功能行为 |
| --- | --- | --- | --- |
| `1.1.28` 及以下 | 原握手 | 保持兼容 | 不接收 1.1.29 新增的健康检查控制消息；限速由 NPS 服务端执行，不要求 NPC 更新 |
| `1.1.29` 及以上 | 随机挑战握手 | 保持兼容 | 接收 Web 配置的健康检查；支持本版本新增的客户端侧连接方式 |

多用户账号、客户端归属、用户级配额及既有 Host/隧道记录不会因升级重新分配。管理面板和 API 仍按当前会话的管理员/普通用户权限过滤数据；不要使用共享 `VerifyKey` 跨用户归属客户端。

## Bridge 可选端口

只有在确实要切换传输方式时才需要开放以下端口：

| 配置 | 用途 | 默认值 |
| --- | --- | --- |
| `bridge_kcp_port` | 额外的 KCP UDP Bridge | `0`（关闭） |
| `bridge_ws_port` | WebSocket Bridge | `0`（关闭） |
| `bridge_wss_port` | TLS WebSocket Bridge | `0`（关闭） |
| `bridge_quic_port` | QUIC Bridge UDP 端口 | `0`（关闭） |
| `bridge_quic_ip` | QUIC Bridge 监听 IP；为空跟随 `bridge_ip` | 空 |
| `quic_alpn` | QUIC TLS ALPN，服务端和 NPC 必须一致 | `nps` |
| `quic_keep_alive_period` | QUIC 保活周期（秒） | `10` |
| `quic_max_idle_timeout` | QUIC 最大空闲超时（秒） | `30` |
| `quic_max_incoming_streams` | 单会话最大并发流数 | `100000` |
| `bridge_path` | WS/WSS 请求路径 | `/ws` |

主 Bridge 的 `bridge_port`、`tls_bridge_port`、`bridge_type` 和现有证书设置不因新增可选端口而自动切换。更改 Bridge 监听或防火墙规则后，需重启 NPS 并确认相应 NPC 传输参数与路径一致。

## 推荐升级流程

1. 在维护窗口停止 NPS，保留旧二进制和完整配置备份。
2. 将 1.1.29 程序放到原安装位置，不改动数据卷和证书目录。
3. 启动 NPS，检查日志是否报告配置迁移失败；如果字段追加成功，日志会列出新增配置键名，不会打印配置值。
4. 确认 Web 管理面板可登录、管理员和普通用户看到的资源范围正确、Host/TCP 访问地址和证书正常。
5. 检查旧 NPC 是否自动重连、原有 TCP/UDP/Host 隧道是否可用。先不要启用额外 Bridge 端口；需要时再逐个配置并验证。
6. 观察日志、连接状态和流量后，再逐步升级 NPC。旧 NPC 可继续保留，不要求同一时间升级。

## 回滚

1. 停止 1.1.29 NPS，恢复原服务端二进制。
2. 如需完全恢复配置文本，恢复升级前备份的 `nps.conf`；否则新增项通常会被旧版本忽略，但备份回滚更容易核对。
3. 保留原 JSON 数据和证书。若 1.1.29 已写入新的 JSON 字段，旧版本会忽略未知字段；若目标旧版本不接受这些字段，再恢复对应 JSON 备份。
4. 启动旧版并确认 NPC 自动重连。不要删除 `instance.key`，除非同时接受所有 Web 会话失效。
