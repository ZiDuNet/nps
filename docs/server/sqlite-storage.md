# SQLite 数据存储与升级

> 自 v1.1.49 起，SQLite 是默认业务数据存储。本文的自动迁移流程适用于 v1.1.52 及后续版本。若使用已发布的 v1.1.49、v1.1.50 或 v1.1.51 首次导入旧 JSON，须按[对应版本说明](../upgrade-sqlite.md#版本选择)先运行 JSON 网关。生产升级前请在副本上演练。

## 版本边界

SQLite 是客户端、用户、隧道、域名规则、全局资源和业务配置的权威存储。`nps.conf` 继续保存进程启动所需的监听、端口、TLS 和程序日志等参数。迁移仅影响 NPS 服务端，无需更新 NPC 或重发连接命令。

| 配置目录状态 | 支持自动迁移的新版本怎么处理 |
| --- | --- |
| 全新安装，无真实旧业务 JSON（空文件、内置样例不算） | 初始化精简的 `nps.conf` 和空的 `nps.db`；不执行旧数据迁移，不生成迁移备份或迁移报告。 |
| 旧版 JSON 数据存在，还没有 SQLite | 正常启动时自动备份、校验和导入；无需先手工运行 `-json-gateway`。 |
| 已有 SQLite | 直接使用现有数据库，不再次导入旧 JSON。只有本次自动迁移标记为待收尾时，才重试清理；不自动处理 v1.1.49、v1.1.50、v1.1.51 留下的历史备份或残留文件。 |

## 数据目录

| 路径 | 用途 |
| --- | --- |
| `conf/nps.conf` | 进程启动参数；迁移前的原文在备份包内 |
| `conf/nps.db` | SQLite 权威数据库 |
| `conf/nps.db-wal` | WAL 日志；运行中可能包含尚未合并的数据 |
| `conf/nps.db-shm` | WAL 共享内存索引 |
| `conf/nps.db.lock` | 单进程实例锁 |
| `conf/backups/pre-sqlite-*.tar.gz` | 仅自动迁移旧数据时生成，保存和校验清理前的旧 `conf` 快照 |
| `conf/migration-report.json` | 旧数据自动导入与收尾的结果；全新安装不生成 |

不要只备份或复制 `nps.db`。运行中的一致性备份必须包含 WAL 和 SHM；最稳妥的方式是先停止 NPS，再复制整个 `conf` 目录。

```bash
sudo nps stop
sudo cp -a /etc/nps/conf "/etc/nps/conf.manual-backup.$(date +%Y%m%d-%H%M%S)"
sudo nps start
```

Unix 上数据库、WAL、SHM 和锁文件权限为 `0600`。迁移备份包含原始密码、密钥或证书材料，请限制 `backups/`、备份包和导出目录的访问，不要放到站点公开目录。Windows 部署请设置等价的 ACL。

## 启动迁移

先停止旧 NPS，确认没有其他旧进程占用同一目录，再独立备份整个 `conf`；存放在目录外的证书、日志或其他运行文件按需另做备份。确认磁盘能同时容纳原文件、迁移备份、临时文件和 SQLite。用新二进制或镜像按原配置目录正常启动即可，与用什么方式替换二进制无关。仅查看状态、打开管理菜单、停止或卸载服务不会触发迁移；通过菜单或服务管理器启动的 NPS 进程才会执行迁移。

1. 将原始 `conf` 写入 `conf/backups/pre-sqlite-*.tar.gz` 并验证归档；不会递归打包备份目录。Docker 使用整个 `/conf` 挂载时，备份留在挂载内。
2. 在临时副本中整形旧 JSON，并校验客户端、用户、隧道、Host 的数量、ID、归属和跨用户路由冲突。已经整形的数据不会再次换算单位。不要手工伪造或修改 `.json-gateway`。
3. 将业务实体、全局数据以及原 `nps.conf` 中的业务配置导入 SQLite 并校验。
4. 确认入库后精简当前 `nps.conf`，只清理本次已备份且能核对内容的旧业务 JSON、网关标记及已识别的迁移遗留文件。保留证书、私钥、`instance.key`、免登设备、用量历史、Geo 数据、日志、未知文件和独立备份。
5. 查看启动日志和 `conf/migration-report.json`。`status=success` 表示本次导入及收尾成功；核对归档路径和实体、设置数量。

备份、数据校验或导入失败时，不清理原文件；按错误提示修正后再启动。若数据库已提交而收尾失败，不要删除 `nps.db` 或复制旧 JSON 覆盖它。检查文件权限、剩余空间和原归档是否可读，保留该归档并重新启动；程序会用同一份已验证归档重试尚未完成的收尾，不会再次导入或删除未核对的文件。

如果同时存在旧 JSON 和没有实体、设置或完成记录的空数据库，新版会停止启动，防止把旧版中断的迁移当成空面板。先独立备份，再在副本中验证恢复。

## 业务配置

迁移完成后，原始 `nps.conf` 保存在备份包内。当前文件保留启动参数、未知自定义键和有效的启动配置；只移除已入库的业务键及已明确废弃的键，不把启动配置文件整个删掉。`include` 引用和非当前运行模式的业务配置原样保留。首次导入后业务配置只以 SQLite 为准：在 Web 面板修改或删除的设置不会因重启被旧文件覆盖。`include` 引用到 `conf` 目录之外的文件需要另外备份。

- 保留在 `nps.conf`：监听地址、端口、TLS 证书路径、程序日志路径 `log_path`、
  运行模式、未知自定义字段等进程启动参数。
- 存入 SQLite 的 `settings` 表：注册策略、用户默认配额、SMTP、HTTP 超时、
  审计日志路径 `audit_log_path`、连接日志路径 `connection_log_path`、
  PoW/TOTP、MCP 开关等业务配置。日志文件本身不会被迁移或清理。

「系统 → 全局参数 → 服务端配置」按用途分为“入口与转发”“Bridge 与客户端”
“日志与监控”“账号与接入”“运行与安全”和“`nps.conf` 启动项”六个 Tab。
前五个只展示 SQLite 业务配置，最后一个集中展示启动参数、兼容/自定义字段和
完整源码。字段卡片的“SQLite 业务配置”/“nps.conf 启动配置”徽标表示权威
来源，“立即生效”/“需重启”徽标表示保存后的运行时行为。回滚不要直接复制
`settings` 表的内容，应使用下方的导出命令。

## 维护命令

维护前先停止使用目标配置目录的 NPS。`nps.db.lock` 会阻止第二个进程同时使用同一数据库；它不能阻止旧 JSON 版本改写原文件。

`-json-gateway` 仍可用于独立旧数据副本的手工整形，命令执行后退出；新版日常启动与升级无需执行它。确需回退到已发布的 v1.1.49、v1.1.50、v1.1.51 并让其从旧单位 JSON 重新建库时，才按目标版本的说明执行网关：

```bash
./nps -conf_path=/data/nps-legacy-copy -json-gateway
```

导出为旧版可读取的 JSON 目录：

```bash
./nps -conf_path=/etc/nps -export-json=/var/backups/nps-json
```

导出内容包括：

- `conf/clients.json`、`users.json`、`tasks.json`、`hosts.json`、`global.json`；
- 合并了 SQLite 业务配置的 `conf/nps.conf`；
- 输出根目录的 `migration-report.json`。

导出会把 bps 转回旧版 KB/s，并按旧版格式写入流量配额；不会生成表示“已整形为 SQLite 单位”的 `.json-gateway`。旧 JSON 版本可直接读取，支持自动迁移的新版可从独立导出目录正常启动并重新入库。若用户配额中的 `0` 表示“套餐不包含”，旧 JSON 无法无损表达，导出会拒绝并写入失败报告。此时应保留 SQLite 数据，或先在面板中改成旧格式能表达的值。

## 一致性设计

- 用户级共享并发连接和双向共享带宽由运行期状态维护；配置修改不会绕过正在使用的连接。
- 客户端、用户及其隧道/Host 级联删除在一个持久化操作中提交，失败时恢复内存记录。
- 平台泛域名与关联 Host 的证书路径在同一事务内保存。
- 周期持久化按行比较，仅更新发生变化或新增的实体，并删除已不存在的行；不再整表删除后重插。
- 持久化资源 ID 跨重启只增不复用；SQLite 在实体事务中同步保存 ID 高水位，删除最大编号后也不会回退计数器。
- 单进程锁防止两个 NPS 进程同时写同一个数据库。

旧 JSON 多文件后端只保留给迁移、测试和嵌入式调用。它无法把 `clients.json`、`tasks.json`、`hosts.json`、`users.json` 等多个文件作为一次原子事务提交；生产启动只要没有显式处于 JSON 维护流程，就会使用 SQLite 作为权威存储。不要把测试环境中直接构造的 JSON 后端当成生产级回滚目标。

## 回滚

精确回滚到升级前状态时，停止 NPS，在独立目录解开对应的 `conf/backups/pre-sqlite-*.tar.gz` 或恢复升级前的停服备份，核对后再用原版本运行。已在升级前手工整形的 JSON 如需交给旧 JSON 版，应使用整形前的备份。该方式不保留升级后的新修改，不要把解出来的旧 JSON 直接覆盖到原 SQLite 目录。

需要回到 JSON 版本但保留 SQLite 当前数据时：

1. 停止 NPS。
2. 执行 `-export-json` 到独立目录。
3. 检查导出的 `migration-report.json.status` 为 `success`。
4. 核对配置。导出不替代整目录备份，证书、私钥、实例密钥等依赖文件按原路径另行恢复，再用导出目录启动仍支持 JSON 的目标版本。
5. 不要同时把旧 JSON 启动结果写回原 SQLite 目录。

## 验收清单

- 只有从旧 JSON 迁移的部署才需要确认 `conf/backups/pre-sqlite-*.tar.gz` 可读，且本次 `conf/migration-report.json` 显示 `status=success`，业务实体和设置数量符合预期。
- `conf/nps.db`、`nps.db-wal`、`nps.db-shm` 所在文件系统有足够空间且仅服务账号可读。
- 全局限流、用户共享带宽、最大连接数、到期时间和停用状态均按预期生效。
- 至少验证一次客户端、用户级联删除，并确认关联隧道和 Host 不残留。
- Docker 已挂载整个 `/conf`，不是只挂载单个 `nps.conf`。
- 已完成一次停服备份和一次 `-export-json` 演练。
